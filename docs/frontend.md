# Frontend

The store and the backoffice. Back to the [README](../README.md).

## Overview

`frontend/` is a pnpm and Turborepo workspace with two Next.js apps joined with [Multi-Zones](adr/0007-frontend-zones-session-and-csp.md): `apps/store` at `/` and `apps/backoffice` at `/admin`. Shared code is in `packages/`: `config` (ESLint, tsconfig, Jest preset, the Tailwind theme and the Next.js configuration), `ui` (components with Storybook), `api-client` (types generated from the services' OpenAPI documents and a small typed fetch wrapper that understands `application/problem+json`), `auth` (server-side session handling) and `web-core` (logic and hooks both apps share: URL search parsers, failure handling and the navigation context; no visual components).

```bash
nvm install && nvm use         # installs the Node version in .nvmrc (the root and frontend/ files hold the same one)
corepack enable                # uses the pnpm version pinned in package.json
make install-frontend
make storybook                 # http://localhost:6006
make test-frontend             # Jest with an 85% coverage threshold per package
make test-storybook            # builds Storybook and runs axe on every story
make lint                      # backend and frontend linters and typechecks
```

If `pnpm -v` does not print the version pinned in `frontend/package.json`, another pnpm (for example a Homebrew one) comes first in your `PATH`; the make targets run `corepack pnpm` from inside `frontend/`, where Corepack reads the pinned `packageManager` (Corepack looks at the package.json of the current directory, not at `--dir`), so they use the pinned version on a machine that has never run Corepack.

- **Styling.** Tailwind v4 is the only styling approach. `packages/config/styles/theme.css` is the single source of design tokens (warm palette, Inter and Playfair Display self-hosted through Fontsource, radii, breakpoints). A test checks every text and control colour pair for WCAG 2.2 AA contrast, and another one fails on removed or misused tokens in component sources.
- **API types.** `backend/tools/dump_openapi.py` writes each service's OpenAPI document to `frontend/packages/api-client/openapi/` and openapi-typescript generates the types. `make openapi` regenerates both; `make check-openapi` (a CI job and a backend test) fails when they are stale.
- **Sessions.** Tokens live in `httpOnly`, `SameSite=Lax` cookies, never in `localStorage`. The Next.js servers call login, register and refresh through the gateway and forward the visitor's address, so the gateway rate limits stay per client. The design, what is proven and what is not are in [ADR 0008](adr/0008-gateway-forwarded-headers-and-rate-limits.md); `make check-rate-limit` runs the proof.
- **Security headers.** Strict, nonce-based Content Security Policy (fonts only from `'self'`), `X-Content-Type-Options`, `Referrer-Policy`, frame and permissions headers. Because a nonce is per response, every page is rendered dynamically; the trade-offs, the refresh deduplication that only works inside one Next.js process, and the deprecated Storybook test runner we keep on purpose are in [ADR 0007](adr/0007-frontend-zones-session-and-csp.md).
- **Routes.** `make check-routes` proves against the running stack that `/` (a temporary redirect to `/products`), `/products`, a product page, `/login` and `/account` reach the store, `/admin` reaches the backoffice, and that no zone route shadows `/api/v1`, `/media`, `/auth`, `/catalog` or `/accounts`.
- **Images.** Both apps build from `frontend/` with multi-stage Dockerfiles (Next.js standalone output, non-root user, pinned base image) and copy only the packages they use, so `make up` twice in a row recreates nothing, and editing one zone rebuilds only that zone.

### Backoffice

`/admin` signs administrators in (`/admin/login`; customers and anonymous visitors are sent back to it) and manages the catalog. It covers sign in and out, the product list, creating, editing, deleting and adding images to products, categories and the users page; the CSV import flow.

- **Everything goes through the Next.js server.** The browser never calls the API: server components read, server actions write, and image uploads stream through a route handler to the gateway without being buffered (limit enforced by `Content-Length` and by counting bytes). The reasoning, including why those routes bypass `proxy.ts`, is in [ADR 0009](adr/0009-backoffice-data-access-and-uploads.md).
- **Navigation.** The shell links to Products, Categories, Users and Orders. CSV import is not a separate section: the products page has an "Import CSV" button that opens `/admin/products/import`.
- **Products list.** Search, category, price range, availability, sort, page size and cursor live in the URL (`nuqs` + Zod): invalid values are ignored, defaults are not written, the cursor is cleared when a filter changes, and back and forward restore each state. The result count is announced with a status region and shown as approximate when the backend estimates it. On narrow screens the table becomes cards.
- **Categories.** The list and a create form (the API has no update or delete). A duplicate name, or one with the same slug, is shown on the field; names are validated like the backend does (whitespace collapsed, at most 100 characters, at least one letter or digit).
- **Users.** Email prefix, role and page size live in the URL like the product filters. The accounts API is forward-only, so there is "Next" and "First page" but no previous page and no total. A role change asks for confirmation and goes to the auth service; the API refuses an administrator changing their own role (`409`) and the dialog shows that. The accounts copy of the role is updated by an event, so the list shows the new role immediately and the server catches up a moment later; the user's current session keeps its old role until it refreshes (at most 15 minutes).
- **CSV import (`/admin/products/import`).** Linked from the products page, not from the navigation. The file goes through a guarded route handler (`/admin/api/stream/imports`) that streams it to the catalog API like the image upload does: it is never buffered, `IMPORT_MAX_BYTES` (50 MB by default, the same variable the backend reads) is enforced by `Content-Length` and by counting bytes, and the browser refuses a bigger file before sending it. The page then follows the import with TanStack Query: it polls with a growing delay, stops when the import is validated, rejected, completed or failed, and announces each status change in a polite live region. The report shows the counts (to create, update, restore, unchanged, errors, warnings), unknown categories grouped with the suggested existing name and a "Create category" button each (the Part B category creation), the problems with a severity filter and cursor pagination, and a `problems.csv` download. Confirming needs a validated import with importable rows and an explicit dialog; after creating a category, "Validate again" calls `POST /imports/{id}/revalidate`. The import id lives in the URL (`?import=<id>`), so a reload or a pasted link opens the same import.
- **Product form.** React Hook Form with a Zod schema that mirrors the backend rules, focus on the first invalid field, backend Problem Details shown on the fields. Edit sends `If-Match`; a `412` opens a dialog that shows the differing fields and lets the administrator choose between the latest version and their own input.
- **Testing deviation.** The project specification mentions MSW for mocking the API. Because every API call is made by the Next.js server, the tests mock `fetch` at that boundary instead and the project avoids one dependency.



### Store

`/` redirects (307, query string kept) to `/products`, the product search, and `/products/{sku}` is the product page. Both are server components, so the first response already has the results; they are public, and the visitor's address is forwarded like in the backoffice. The decisions are in [ADR 0010](adr/0010-store-catalog-search-and-product-pages.md).

- **Search state lives in the URL.** `q`, `category` (slug), `min_price`, `max_price`, `in_stock`, `sort`, `limit` and `cursor` are parsed with the `web-core` parsers (the ones the backoffice uses): an invalid value is ignored and defaults are never written. Every filter change is a history entry (`router.push` through nuqs), so back and forward walk the filters; the search text is applied 300 ms after the last keystroke; any filter change drops the cursor. Previous and Next carry the cursor in the URL, so a pasted link opens the same page. A total that is only an estimate reads "About 1,200 results".
- **Filters.** A sidebar from the `lg` breakpoint and a drawer below it (Radix Dialog: focus trapped, Escape closes, focus returns to the button that opened it). Active filters are removable chips with a "Clear all filters" button. The grid has 1, 2, 3 and 4 columns from the `sm`, `lg` and `xl` breakpoints. The total is announced through the pagination live region.
- **Product page.** The SKU is case-insensitive: another case redirects to the canonical address. Unknown and retired products are a real 404 with a page that links back to the catalog, and a temporary catalog failure shows an alert with a retry link instead. Out of stock products stay visible with their badge and a notice, and show no purchase action.
- **Images.** Cards use the 400 px thumbnail and the product page the 1200 px image; a product without an image, or whose image fails to load (also before hydration), shows the placeholder. `MEDIA_PUBLIC_BASE_URL` is relative, so the URLs are same-origin and the CSP needs nothing extra.
- **Customer accounts.** `/register` creates the account and signs in with the same credentials; `/login` signs in. Both are server actions over `packages/auth`, so the tokens only ever live in the `httpOnly` cookies. An email that is taken is shown on the email field (with a link to sign in), password rules from the API (too short, too common, same as the email) are explained in plain language on the password field, and a rate limit says when to retry. `next` is only accepted as an internal path (`nextPath` in `web-core`, the same helper and open-redirect table the backoffice uses); anything else, and the login and register pages themselves, fall back to `/products`. The header shows Sign in to a visitor and Account and Sign out to a customer. `/account` reads the profile from `GET /api/v1/accounts/me` and edits name and phone with `PATCH` (a blank phone clears it); field errors are linked to their inputs and focus goes to the first invalid one.
- **Cart.** The product page has the add to cart action in its slot: a quantity (1 to 99, never above the stock) and a button that is disabled, with the reason, when the product is out of stock. A visitor who adds goes to `/login?next=/products/{sku}`. Signed in customers see a Cart link with the number of units in the header; a polite live region announces the new count when it changes. `/cart` (protected like `/account`; the cart service documentation is under `/cart-service`) lists each line with image, name, quantity control, line total and Remove, a subtotal, an empty state and Clear cart behind a confirmation dialog. Every call goes through the store server with the session cookie. A price change shows as "The price changed from $X to $Y" with Accept new price (it sends `accepted_price`; on a `409` the page shows the price the server reported and the next click accepts that one), a retired product as "No longer available" and low stock as "Only N left" or "Out of stock". The cart limits (100 different products, 1 to 99 per product) and an unreachable cart are shown as plain messages, the latter with Try again. Changes are announced in `role="status"` regions and focus returns to the page heading when the cart empties. See [ADR 0010](adr/0010-store-catalog-search-and-product-pages.md).
- **Checkout (`/checkout`).** Protected like `/account`. The server builds the order from the cart service and the saved address, never from what the browser sends; flags on a cart line block checkout. The card field is `inputmode="numeric"`, grouped by four, cleared after every submit, and the page says visibly that payments are simulated and lists the four test cards. One `Idempotency-Key` per attempt makes a double click one order. Details in [ADR 0016](adr/0016-store-checkout-and-order-tracking.md).
- **Order tracking (`/orders/{id}`).** The server renders the order, then a client component polls `/api/orders/{id}` (growing delay up to 8 s) until `CONFIRMED` or `CANCELLED`. The status is one polite live region with text and an icon, never colour alone, and a cancelled order explains why (out of stock, price changed, payment declined, payment timed out) and whether a late payment was refunded.
- **Order history (`/orders`).** The customer's orders, newest first, 25 per page; the cursor lives in the URL. The header links to it. The backoffice has `/admin/orders` and `/admin/orders/{id}` (read only, with the customer email snapshot, payment and status history), see [ADR 0017](adr/0017-order-views-and-customer-email-snapshot.md).
- **Not found.** The store and the backoffice have their own root `not-found` page, because Next's default one carries an inline `<style>` that the nonce policy blocks. `make check-not-found-csp` checks it against the running stack.

### Accessibility

Automated: axe runs on every Storybook story (`make test-storybook`, WCAG 2.0 to 2.2 A and AA rule sets) and on the rendered components in the Jest tests (`jest-axe`); a test checks every text and control colour pair for AA contrast; interactive primitives are Radix (focus trap, Escape, focus return, keyboard navigation); status changes use polite live regions and never rely on colour alone.

Not done: a manual pass with a screen reader (VoiceOver or NVDA) over the purchase flow was **not performed**. Treat the claims above as what the tools can prove, not as a complete WCAG audit.
